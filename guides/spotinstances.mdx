### Intro
Spot instances let you rent GPUs at a discounted hourly price in exchange for interruptibility:
the capacity may be reclaimed at any time, at which point the instance is terminated.
They are a great fit for fault-tolerant workloads like batch inference, hyperparameter sweeps,
checkpointed training, and CI jobs — anything that can stop and resume without losing work.

On-demand instances are never interrupted; only instances you explicitly launch with the
spot rental type are.

### Finding spot capacity
Spot is offered on select instance types, on Shade Cloud and on participating partner clouds.
The catalog is the source of truth for which. To see them, call the
[Instance Types API](/api-reference/instances/instances-types):

<CodeGroup>
  ```bash curl
  curl --request GET \
  --url 'https://api.shadeform.ai/v1/instances/types' \
  --header 'X-API-KEY: <api-key>'
  ```

  ```bash CLI
  shade instances list-types
  ```
</CodeGroup>

Every entry in an instance type's `availability` array carries a `rental_type`. Regular entries
are tagged `rental_type: "on_demand"`; instance types that support spot list an additional entry
per region marked `rental_type: "spot"`, carrying the spot hourly price as a decimal string in
dollars:

```json Availability
"availability": [
  {
    "region": "us-central-1",
    "available": true,
    "display_name": "US, Wichita, KS",
    "rental_type": "on_demand"
  },
  {
    "region": "us-central-1",
    "available": true,
    "display_name": "US, Wichita, KS",
    "rental_type": "spot",
    "hourly_price": "1.50"
  }
]
```

Spot and on-demand availability are evaluated independently — a region can offer spot while
on-demand is sold out, and vice versa — so always read the entry matching the rental type you
intend to launch. Because a region can appear twice, filter the array by `rental_type` rather
than treating it as one entry per region.

### Launching a spot instance
Add `"rental_type": "spot"` to your [Create Instance API](/api-reference/instances/instances-create) request,
using the `cloud`, `region`, and `shade_instance_type` from a catalog entry that offers spot.
Spot instances are always launched with Shadeform's own provider accounts, so `shade_cloud`
must be `true` regardless of the cloud:

<CodeGroup>
  ```bash curl
  curl --request POST \
  --url 'https://api.shadeform.ai/v1/instances/create' \
  --header 'X-API-KEY: <api-key>' \
  --header 'Content-Type: application/json' \
  --data '{
    "cloud": "excesssupply",
    "region": "us-central-1",
    "shade_instance_type": "A6000",
    "shade_cloud": true,
    "name": "spot-example",
    "rental_type": "spot"
  }'
  ```

  ```bash CLI
  shade instances create \
    --cloud excesssupply \
    --region us-central-1 \
    --shade-instance-type A6000 \
    --shade-cloud=true \
    --name spot-example \
    --rental-type spot
  ```
</CodeGroup>

`rental_type` is optional and defaults to `"on_demand"`. Omitting it — as every request written
before spot existed does — launches a regular on-demand instance, so existing integrations are
unaffected; you only get a spot instance by asking for one explicitly.

If the instance type does not offer spot in that region, the create request fails with a
descriptive error — you are never silently given an on-demand instance at the on-demand price.

You can also launch spot instances from the platform by flipping the spot toggle in the
launch flow; the discounted price is reflected before you deploy.

### Checking rental terms
Instance list/info responses include a `rental_terms` object describing how each instance is rented:

```json Rental Terms
"rental_terms": {
  "rental_type": "spot",
  "hourly_price": "1.50",
  "ending_at": null
}
```

`rental_type` is `spot` for spot instances and `on_demand` for everything else, including
instances launched without a `rental_type` in the request. `hourly_price` is a decimal string
in dollars — for a spot instance this is the discounted rate you are billed at. `ending_at` is
the promised end of the rental when one is known, and `null` for open-ended rentals. Spot
instances are open-ended and can be reclaimed at any time, so `ending_at` is `null`; a reclaim
shows up as the instance moving to `deleting` with `"status_details": "preempted"` (see below).

### Interruption behavior
A spot instance is terminated when the capacity is needed elsewhere, and billing stops. On
Shade Cloud that happens when on-demand demand needs the hardware. On a partner cloud it happens
when the partner needs the capacity or when the partner's spot market price rises above what
Shadeform will pay for it; your price never changes either way, and the outcome is identical.
A reclaimed instance is distinguishable from one you deleted yourself: its terminal state
carries `"status_details": "preempted"` in the
[Instance Info API](/api-reference/instances/instances-info) response.

Expect little or no advance warning. Some backends send a `SIGTERM` to processes inside the
VM shortly before stopping it (on the order of a minute); none publish a deadline through the
API, so `ending_at` stays `null`. If your workload can act on it, trap `SIGTERM` to flush a final
checkpoint.

Design your workload to tolerate interruption:

- Checkpoint progress to a mounted [volume](/guides/attachvolume) or external storage.
- Make jobs idempotent and resumable so a replacement instance can pick up where the last one left off.
- Poll your instances and relaunch (spot or on-demand) when one is reclaimed.

### Restarting a spot instance
The [Restart API](/api-reference/instances/instances-restart) is not available for spot
instances on some partner clouds and returns a `NOT_SUPPORTED` error there. Use `sudo reboot`
from inside the instance instead; it keeps the instance and its disk.

Do not power a spot instance off from inside (`poweroff`, `shutdown -h`, `halt`). On those
clouds a powered-off spot instance cannot be told apart from one the provider reclaimed: it
is treated as preempted, billing stops, and the instance and its disk are deleted.

### Pricing
Spot pricing is set per instance type and shown on the `rental_type: "spot"` catalog entries.
Billing works exactly like on-demand — per-second metering at the spot rate — and stops when
the instance is reclaimed or deleted.
